# A guided first session

The user may know nothing about Steward, skills, vaults, or what to ask. Own the next step. Explain enough to make each choice easy, do the authorized work, and show its result before moving on. Reuse known answers and resume the saved step. A direct request or skipped onboarding still takes its direct route.

## 1. Welcome and memory

Explain the benefit and the short path before asking a question. For example: “I'm Steward. I help turn the things on your mind into plans that fit your life, and keep track of where we left off. We'll set up a place to remember things, connect the apps you choose, then find one thing I can help with today. I'll walk you through it.” Adapt to the user's tone; this is an example, not a repeated greeting.

Use [setup](setup.md). Recommend Obsidian for a new personal wiki: it is an app for browsing and editing the same plain-text notes Steward uses. Explain that it is optional, that an existing vault works, and that a plain folder works too. Offer a sensible location rather than making a novice invent a filesystem path. Ask one unresolved choice, such as “Do you already use Obsidian, or shall we start a new memory folder?” Preserve the user's vault name. A no-storage trial remains available.

Create or adapt the actual wiki, not just a promise to remember. Finish: navigate from its Home to source, knowledge, current work, history, and deliverable indexes (or their existing equivalents); verify saved state and trusted retrieval. Explain what is ready and the exact next step if app setup still needs the user. Do not label a local readback as a successful fresh-task test.

## 2. Connect and get acquainted

Use [connections](connections.md) to discover the host's actual tools, offer useful available sources, and save the user's choices. Explain the first review before they select apps: “I'll look at upcoming commitments, open tasks, and recent relevant notes or conversations, then bring back a few ways I could help. I'll keep shared spaces read-only and ask before sending anything.” The offered scope and exclusions govern the read. Selecting all offered sources authorizes that explained review, not unlimited historical collection.

After connection checks, perform the initial review in [connected context](../../steward-memory/references/connected-context.md) now. A successful list of calendars or accounts is not a review of their contents. Check selected sources across the agreed scope, save coverage and useful evidence, and distinguish a partial picture from a complete review. Discover relevant non-Apple connectors too. Finish: actual content reviewed or an honest gap with a specific recovery step for each selected source; no installed-only or metadata-only source marked reviewed.

For a blocked app, try an available supported alternative route within the same scope. Guide any necessary manual action one step at a time, using actual tool output or current documentation. Explain what can continue meanwhile and keep the repair pending. Never tell the user a mention will expose tools unless that host behavior is verified.

## 3. Give the user something to choose from

Bring back two or three useful, evidence-backed possibilities in plain language: the task, why it may help, and what you can actually do. Include coverage limits briefly. For example, an approaching reimbursement deadline can support a proposal to prepare the claim; a trip note without a deadline does not establish the user's highest priority. Ask which to take on, with an easy alternative: explore an area of life. Do not substitute a vague “What do you want?” for this first demonstration.

If there is little usable context, lead with the alternative: “We can start with one part of life you'd like to make easier. Health and energy, money, work, relationships, or home are common starting points. Which feels closest?” Use [focus](../../steward-focus/SKILL.md) and the [area menu](life-areas.md) as helpful prompts, not a full life audit. If several concerns emerge, reflect them, offer a tentative starting point with a reason, and let the user choose. Financial difficulty alone does not establish an emergency or displace their chosen health focus.

Finish: a user-chosen direction. A proposed focus stays proposed until accepted. If the user corrects an inference, propagate the correction and continue discovery from other available evidence before asking them to recreate their task list.

## 4. Carry the first useful thing through

Load the relevant specialists yourself. An ongoing outcome can proceed through focus, goals, plan, routines, schedule, and review without the user naming those skills. Recover context before each decision-changing question. Ask only for the missing fact or preference that changes the next step, not an intake form of information available in connected sources.

For a chosen goal, define a workable success signal, prepare the first action, and offer a realistic routine or time slot based on actual availability. When the user authorizes placement or reminders, create them in the chosen private destination, read them back, and report what actually happened. Goal approval alone does not authorize live writes. If a route is blocked, finish the plan and retain the specific unapplied action and recovery step, rather than pretending it is scheduled. A small request can end with its useful result without inventing a goal.

Finish: an artifact or verified action the user can use, not merely advice on how to use Steward. Save the chosen goal, relevant knowledge with provenance, result, and next step to the wiki, with working index links. Keep unknowns unknown.

## 5. Leave an easy way back

Use [session state](session-state.md) and [memory](../../steward-memory/SKILL.md). Say what was done and what comes next, then explain once: “Come back with whatever comes up, or say ‘What next?’ I'll pick up from here.” Only promise continuity after the store and retrieval route are verified. A no-storage trial gets a portable continuation note. Requested scheduled check-ins use schedule; a skill alone does not run in the background.

Onboarding is complete or explicitly limited when memory choice, connection choices, initial review or skip, a chosen direction, one useful result, and a saved return point are resolved. Optional app failures remain visible pending items, not a reason to restart onboarding. Save progress when interrupted.
