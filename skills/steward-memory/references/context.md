# Acquire context and propagate changes

Start from the decision, not a questionnaire. Inspect relevant conversation, saved context and connected sources within the authorized task. Use health, finances, calendar, messages, files, location, household resources and current research only where they materially change the outcome. More context is useful when it changes a decision, not merely because it exists.

For live apps, use [connected context](connected-context.md) to recover saved selections, scope, and access evidence before retrieving data.

Before asking, distinguish:

- **Known:** directly reported or observed, with source and freshness.
- **Target:** the user wants it; it may not yet be true.
- **Belief:** a proposed mechanism or strategy, distinct from the underlying value.
- **Uncertain:** inference, stale data, ambiguous identity, unavailable record or missing fact.

Reconcile sources rather than silently picking one. Absence of transactions is not absence of household spending. A missing workout log is not proof no exercise happened. City-level location is not a home address. A bottle color is not a confirmed supplement or dose. Ask only the unresolved fact that matters.

Use a compact recap before a materially new Plan or after decision-changing corrections. Let the user correct facts and add context. A recent explicit confirmation need not be requested again. Pending questions should block only the dependent work; provisional artifacts must label their assumptions.

## Preferences should be easy to express

When the user cannot name preferences, find and filter a small set of strong, concrete options. Ask which look good, bad or acceptable; avoid asking them to invent a list. Carry corrections into later choices. An ingredient preference can differ from its preparation: liking tofu does not imply liking scramble; liking beans does not imply liking salads. A nutritionally efficient choice must still fit the person's taste, budget and time. Solve resulting shortfalls elsewhere.

Look for existing resources and control: who pays, shops, cooks, owns the equipment, controls the calendar, or must agree? A family-funded grocery list can be more feasible than personal purchases. Respect the user's actual platform and workflow.

## PROPAGATE CONTEXT

For a decision-changing update:

1. Record the new fact with source, date and certainty; retire the old assumption.
2. Trace connected goals, rules, routines, plans, artifacts and live actions. Include second-order effects.
3. Recompute the affected schedule, quantities, instructions and costs. Check feasibility and parent-goal conflicts.
4. Present the meaningful changes together. Update authorized saved plans; prepare required live edits under the action policy.
5. Verify affected live updates, mark obsolete artifacts, and carry unresolved decisions forward.

For example, a new eating-window rule changes meals, portions, nutrition, shopping, prep, training/recovery timing, supplements, sleep interaction and calendar blocks. Derive clock times only from confirmed anchors. If the sleep anchor itself is still a target, distinguish current and eventual schedules.

When conflict appears, climb to the shared parent goal and distinguish the user's value from their chosen strategy. Research the tradeoff before choosing a winner. New priorities may change the nominal goal itself.
