# Shared working context

This suite shares one operating contract. Read it once per task when a Steward skill applies; then load only the references required for the current work. The full suite is installed as sibling folders so these links resolve. If a required sibling is missing, report the packaging problem and finish unaffected work; do not invent its contents.

The user chooses what matters. Skills remove reasonable research, coordination, setup, and remembering overhead. Personal examples are never defaults. When live app context can change the work, read [connected context](connected-context.md) to use the user’s selected sources and scopes. Acquire relevant context before asking the smallest question that changes a decision; use [context](context.md) for acquisition, preferences, and propagation, and [model](model.md) when organizing records or dependencies.

Recover the selected area/goal, current plan, constraints, pending decisions, and **prototype or active mode** from available context. Mode persists: “looks good” or plan approval does not activate live actions. A goal being active is separate from action authorization. Before capability discovery, scheduling, external writes, or resolving lingering live items, read [actions](../../steward-admin/references/actions.md). Respect specific authorization already given; prepare a concrete result before any required final approval.

For material decisions or deliverables, use [research quality](../../steward-decide/references/research-quality.md). Keep present baseline separate from aspiration. When strategies conflict, trace their parent goals and the user's values; subjective experience informs fit without proving a mechanism. For every decision-changing fact, use the propagation procedure in [context](context.md): update affected local records and outputs, mark superseded versions, and verify authorized live changes separately.

Choose the skill that owns the requested outcome. A factual correction spanning several goals starts with steward-memory, which tracks the affected records and uses each work owner for substantive changes; a request limited to moving calendar items starts with steward-schedule. Read sibling skill instructions when their distinct work is needed and continue in the same task. A skill boundary is neither a mandatory pause nor a reason to hand work back to the user. There is no fixed pipeline: a simple draft need not create a goal, and a new goal need not create a calendar. If the selected goal is known, “continue” resumes its outstanding work instead of restarting onboarding. When the target is ambiguous, resolve only that ambiguity while doing independent work.

Finish reasonable implementation within scope. Check actual artifacts, calculations, resource needs, recurring steps, and verified action state; use [planning criteria](../../steward-plan/references/planning-deliverables.md) when creating usable outputs. At meaningful planning or completion points, consider a concrete high-value adjacent opportunity; read [opportunities](../../steward-opportunities/SKILL.md) if one is grounded in context. Keep the requested objective primary.

At a material change or stopping point, use [memory](../SKILL.md) to save authorized durable state. If no store is configured, provide a portable continuation note and state the limit. A skill does not remember across sessions or run in the background by itself. Present the result simply using [presentation](../../steward-plan/references/presentation.md), with prepared versus completed actions and only real open items.
